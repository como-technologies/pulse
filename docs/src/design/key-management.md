# Pulse — Multi-Tenancy and Key Management

*Describes the cryptographic isolation model, envelope encryption architecture, and key lifecycle.*

*Parent document: [Architecture](README.md)*

---

## 1. Design Goals

| Goal | Description |
|------|-------------|
| **Tenant isolation** | Compromise of one tenant's data does not expose another tenant's data |
| **Operator zero-knowledge** | The platform operator has zero access to tenant data under any circumstance |
| **Customer control** | Tenants hold their own keys and control their own data destiny |
| **Crypto-shredding** | Deleting the key renders all tenant data permanently irrecoverable |
| **Key loss = data loss** | Irrecoverable by design. The operator cannot help. This is the price of zero-knowledge. |

---

## 2. Key Hierarchy

The system uses a two-tier **envelope encryption** model:

```
Tier 1: Customer-Managed Key (CMK)
  |
  |-- wraps/unwraps -->  Tier 2: Data Encryption Keys (DEKs)
                           |
                           |-- DEK-responses: encrypts response blobs at rest
                           |-- DEK-blindsig: encrypts the blind signature private key
                           |-- DEK-analytics: encrypts client-side response payloads
```

### 2.1 Tier 1 — Customer-Managed Key (CMK)

| Property | Value |
|----------|-------|
| **Held by** | The tenant, in their own key management infrastructure |
| **Stored by Pulse** | Never. Pulse holds only a reference/handle (e.g., a KMS endpoint URL). |
| **Purpose** | Wrap (encrypt) and unwrap (decrypt) Tier 2 DEKs |
| **Rotation** | Managed by the tenant. When rotated, existing wrapped DEKs are re-wrapped under the new CMK. |
| **Loss consequence** | All tenant data becomes permanently irrecoverable |

### 2.2 Tier 2 — Data Encryption Keys (DEKs)

| Property | Value |
|----------|-------|
| **Generated by** | Pulse, at tenant onboarding and as needed |
| **Stored by Pulse** | In wrapped (encrypted) form only, wrapped by the tenant's CMK |
| **Purpose** | Encrypt/decrypt actual tenant data within a specific data domain |
| **Rotation** | Managed by Pulse, coordinated with the tenant's CMK availability |
| **Scope** | One DEK per data domain per tenant (see key domains below) |

### 2.3 Key Domains

Each tenant has separate DEKs for different data domains. This provides defense-in-depth and enables selective access:

| Domain | DEK | What It Protects |
|--------|-----|-----------------|
| Responses | `DEK-responses` | Anonymous response blobs in the Response Store |
| Blind Signature | `DEK-blindsig` | The Token Issuer's private signing key for this tenant |
| Analytics | `DEK-analytics` | Client-side response payloads (Analytics Engine decrypts for aggregation) |

Separate DEKs mean that compromising one domain's DEK (in its unwrapped, in-memory state) does not expose other domains.

> **Future domains:** Additional domains (e.g., question content, org metadata) may be introduced as the system evolves. These are not tracked in the current roadmap.

## 3. Key Operations

### 3.1 Tenant Onboarding

```
1. Tenant provides a CMK reference
   (e.g., an endpoint URL to their KMS, or a public wrapping key)

2. Pulse generates DEKs for each data domain
   (cryptographically random, appropriate key sizes)

3. Each DEK is wrapped (encrypted) using the tenant's CMK
   - If CMK is in an external KMS: Pulse calls the KMS wrap API
   - If CMK is a public wrapping key: Pulse encrypts the DEK locally

4. Wrapped DEKs are stored by Pulse
   (the plaintext DEKs are discarded from memory)

5. The CMK is NEVER stored, cached, or logged by Pulse
```

### 3.2 Data Write (e.g., Storing a Response)

```
1. Service needs to encrypt data for tenant T

2. Service retrieves the wrapped DEK for the relevant domain
   (e.g., DEK-responses for tenant T)

3. Service requests DEK unwrapping from the Tenant Key Gateway

4. Tenant Key Gateway calls the tenant's KMS:
   "Please unwrap this DEK using your CMK"
   (authenticated, authorized, audited call)

5. Tenant's KMS returns the plaintext DEK
   (over a secure, authenticated channel)

6. Service encrypts the data with the plaintext DEK
   (using authenticated encryption: AEAD)

7. Plaintext DEK is discarded from memory after use

8. Encrypted data is stored (ciphertext + metadata)
```

### 3.3 Data Read (e.g., Computing Analytics)

Same flow in reverse: retrieve wrapped DEK → unwrap via tenant KMS → decrypt data → use → discard plaintext DEK.

### 3.4 Tenant Offboarding (Crypto-Shredding)

```
1. Tenant initiates offboarding

2. Tenant deletes or revokes their CMK in their own KMS

3. All wrapped DEKs for this tenant become permanently un-unwrappable
   (the wrapping key no longer exists)

4. All tenant data is now cryptographic garbage
   (encrypted under DEKs that can never be recovered)

5. Pulse can physically delete the ciphertext at leisure
   (or retain it for compliance — it's meaningless without the keys)

Result: Clean, verifiable data destruction without needing to
locate and securely wipe every copy of every data record.
```

## 4. CMK Integration Interface

The Tenant Key Gateway abstracts the CMK integration, supporting multiple KMS backends:

### 4.1 Interface Contract

The tenant's KMS must support (at minimum):

| Operation | Description |
|-----------|-------------|
| `wrap(dek_plaintext) → dek_wrapped` | Encrypt a DEK using the CMK |
| `unwrap(dek_wrapped) → dek_plaintext` | Decrypt a DEK using the CMK |

Optional but recommended:

| Operation | Description |
|-----------|-------------|
| `rotate_cmk()` | Signal that the CMK has been rotated. Pulse re-wraps all DEKs under the new CMK. |
| `key_status()` | Check if the CMK is active, rotated, or revoked |

### 4.2 Supported Integration Models

| Model | Description | Trade-offs |
|-------|-------------|------------|
| **External KMS (API)** | Tenant hosts a KMS (cloud or on-premise). Pulse calls wrap/unwrap APIs at runtime. | Strongest: CMK never leaves tenant's infrastructure. Requires network connectivity to tenant KMS for every data operation. |
| **Wrapping Key (Public Key)** | Tenant provides a public wrapping key. DEKs are wrapped locally by Pulse using the public key. Unwrapping requires the tenant's private key. | Simpler setup. Tenant's private key never leaves their infrastructure. But wrap is one-way — unwrap requires a call to the tenant's infrastructure. |
| **HSM-Backed** | Tenant's CMK lives in an HSM (Hardware Security Module). | Maximum security for the CMK itself. More complex and expensive to set up. |

### 4.3 Availability Considerations

Since every data read/write requires DEK unwrapping, the tenant's KMS is on the critical path:

- **KMS downtime = Pulse downtime** for that tenant's data operations
- Mitigation: short-lived DEK cache. After unwrapping, the plaintext DEK can be cached in memory for a configurable TTL (e.g., 5 minutes). This reduces KMS call frequency while limiting the exposure window.
- The DEK cache is in-memory only, never persisted. Process restart = cache cleared.
- The cache TTL is a trade-off: longer TTL = fewer KMS calls (better availability) but longer window where the plaintext DEK is in memory (higher risk if the process is compromised).

## 5. Blind Signature Key Management

### 5.1 Per-Tenant Signing Keys

Each tenant has its own blind signature key pair:

| Key | Stored By | Encrypted Under | Used By |
|-----|-----------|----------------|---------|
| Private signing key | Pulse (encrypted) | `DEK-blindsig` | Token Issuer — signs blinded tokens |
| Public verification key | Pulse (plaintext) | Not encrypted (public) | Response Collector — verifies signatures |

**Why per-tenant:** Tokens from Tenant A use Tenant A's signing key. The Response Collector for Tenant A only accepts signatures from Tenant A's key. This prevents cross-tenant token use.

### 5.2 Key Rotation

Blind signature keys must be rotatable:

```
1. Generate new key pair (version N+1)

2. Wrap new private key under DEK-blindsig

3. Publish new public key to the Response Collector

4. Token Issuer begins signing with the new key
   (tokens carry a key_version field)

5. Response Collector accepts signatures from both
   version N and version N+1 during the transition period

6. After all version-N tokens have expired (based on their
   expiry timestamps), version N's private key is destroyed
   and its public key is removed from the accepted set

Result: Zero-downtime rotation. No re-signing of existing tokens.
```

### 5.3 Key Compromise Response

If a tenant's blind signature private key is compromised:

1. Immediately rotate to a new key (emergency rotation)
2. Invalidate all tokens signed with the compromised key (set their acceptance window to zero)
3. Re-issue tokens to affected employees via the normal flow
4. The damage is bounded: the attacker can forge tokens, but forged responses are still anonymous (the attacker gains the ability to inject responses, not to deanonymize existing ones)

## 6. DEK Rotation

### 6.1 Strategy: Key Version History

Rather than re-encrypting all stored data under a new DEK (expensive, requires reading/writing every record), the system maintains a version history:

```
DEK-responses-v1 (wrapped) — used for responses stored before rotation
DEK-responses-v2 (wrapped) — used for new responses after rotation
...
```

- Each encrypted record carries a `dek_version` tag
- On read, the correct DEK version is retrieved and unwrapped
- Old DEK versions remain wrapped and available for reading old data
- Eventually, old data can be re-encrypted under the current DEK as a background task (optional, for simplicity)

### 6.2 Rotation Trigger

DEK rotation can be triggered by:

| Trigger | Description |
|---------|-------------|
| Scheduled | Periodic rotation (e.g., annually) |
| CMK rotation | When the tenant rotates their CMK, all DEKs are re-wrapped (not re-generated — just re-wrapped under the new CMK) |
| Incident | Emergency rotation if a DEK is suspected compromised |
| Policy | Tenant's compliance requirements mandate a rotation schedule |

### 6.3 CMK Rotation vs. DEK Rotation

These are distinct operations:

| | CMK Rotation | DEK Rotation |
|---|---|---|
| **What changes** | The wrapping key | The data encryption key |
| **Data impact** | None — data stays encrypted under the same DEK. Only the DEK's wrapping changes. | New data encrypted under new DEK. Old data under old DEK (or re-encrypted). |
| **Cost** | Low — re-wrap each DEK (one operation per domain) | High — either maintain version history or re-encrypt all data |
| **Frequency** | Per tenant's KMS policy (typically annual) | Less frequent (triggers listed above) |

## 7. Data-at-Rest Encryption Summary

| Data | Encrypted? | Under Which Key? | Stored Where? |
|------|-----------|-----------------|---------------|
| Response blobs | Yes (AEAD) | DEK-responses | Response Store (Signal) |
| Client response payloads | Yes (AEAD) | DEK-analytics | Inside response blobs (client-encrypted) |
| Blind sig private key | Yes (AEAD) | DEK-blindsig | Token Issuer (Identity) |
| Blind sig public key | No (public) | — | Response Collector (Signal) |
| Spent-token ledger | Hashes only | — | Response Collector (Signal) |
| Wrapped DEKs | Yes (wrapped by CMK) | CMK | Tenant Key Gateway |
| CMK | N/A | Tenant's responsibility | Tenant's KMS (external) |

## 8. Operator Visibility

What the platform operator can see (even with full infrastructure access):

| Visible | Not Visible |
|---------|-------------|
| Tenant IDs | Response content |
| Data volume per tenant | Question content |
| Request rates and patterns | Employee identity data |
| Encrypted ciphertext blobs | Analytics results |
| Wrapped DEK blobs | Blind signature private keys |
| Blind signature public keys | Pseudonyms |
| System health metrics | Anything requiring a DEK to decrypt |

The operator can run the system, monitor its health, and bill tenants — but cannot access any tenant data content.

## 9. Failure Modes

| Failure | Impact | Recovery |
|---------|--------|----------|
| Tenant's KMS unavailable | Tenant's data operations suspended. New responses queued but not encrypted (or rejected, depending on policy). | Resumes automatically when KMS returns. Queued data encrypted on recovery. |
| Tenant loses CMK | All tenant data permanently irrecoverable. | None. By design. Tenant should be clearly warned during onboarding. |
| DEK corruption (wrapped form) | Affected data domain unreadable for that tenant. | Re-wrap from CMK if the plaintext DEK was cached; otherwise, data loss for that domain. Defense: maintain backup copies of wrapped DEKs. |
| Blind sig key compromise | Attacker can forge tokens (inject responses). Cannot deanonymize existing responses. | Emergency key rotation. Invalidate old-key tokens. Re-issue to affected employees. |

## 10. Compliance Considerations

| Requirement | How Pulse Addresses It |
|-------------|----------------------|
| GDPR right to erasure | Crypto-shredding: delete CMK → data irrecoverable. No need to locate individual records (responses have no PII anyway). |
| Data residency | The Tenant Key Gateway can be configured to use region-specific KMS endpoints. Data storage can be region-scoped. |
| Audit trail | All key operations (wrap, unwrap, rotate) are logged. Logs include tenant_id, operation, timestamp — but never key material. |
| Breach notification | If encrypted data is exfiltrated, it is meaningless without the CMK. Whether this constitutes a "breach" depends on jurisdiction, but the risk to data subjects is effectively zero. |
