# Multi-Tenancy Providers

This guide explains how Pulse's multi-tenancy key hierarchy works and how to implement a production-grade CMK provider (e.g., backed by AWS KMS or GCP Cloud KMS).

---

## Architecture Overview

Multi-tenancy involves several components spread across the domain crates and the composition root. The traits in domain crates define the ports; implementations in `pulse-server` provide the adapters.

### Key Components

| Component | Crate | Role |
|-----------|-------|------|
| `TenantSigningKeyStore` trait | `pulse-identity` | Provide the blind-signature signing key for a tenant |
| `TenantVerificationKeyStore` trait | `pulse-signal` | Provide the blind-signature verification key for a tenant + version |
| `CmkProvider` trait | `pulse-server` | Wrap/unwrap DEKs under a tenant's Customer-Managed Key |
| `DekStore` trait | `pulse-server` | Store and retrieve wrapped (encrypted) DEKs per tenant and domain |
| `EncryptingResponseStore` | `pulse-server` | Decorator that adds envelope encryption to any `ResponseStore` |
| `TenantProvisioner` | `pulse-server` | Orchestrates provisioning of all cryptographic material for a new tenant |
| `InMemoryTenantKeyStore` | `pulse-server` | Dev-mode implementation of both signing and verification key stores |
| `DevCmkProvider` | `pulse-server` | Dev-mode CMK provider (single local wrapping key for all tenants) |
| `InMemoryDekStore` | `pulse-server` | Dev-mode DEK store (in-memory `HashMap`) |

---

## The Key Hierarchy

Pulse uses a two-tier envelope encryption model:

```
                   Tenant's CMK (Customer-Managed Key)
                   held by the tenant, never stored by Pulse
                        |
            +-----------+-----------+
            |                       |
       wraps/unwraps           wraps/unwraps
            |                       |
    +-------+-------+     +--------+--------+     +---------+--------+
    | DEK-responses  |     | DEK-blindsig    |     | DEK-analytics    |
    | (AES-256 key)  |     | (AES-256 key)   |     | (AES-256 key)    |
    +-------+--------+     +--------+--------+     +---------+--------+
            |                       |                         |
     encrypts/decrypts       encrypts/decrypts        encrypts/decrypts
            |                       |                         |
    +-------+--------+    +--------+--------+    +-----------+---------+
    | Response blobs  |    | Blind-sig key   |    | Client-side response |
    | (stored in DB)  |    | material at rest|    | payloads (analytics) |
    +-----------------+    +-----------------+    +----------------------+
```

- **CMK (Customer-Managed Key)** -- Held by the tenant in their own KMS. Pulse never stores it. The `CmkProvider` trait wraps and unwraps DEKs by calling out to the tenant's KMS.

- **DEKs** -- Each tenant has independent 32-byte AES-256 keys for each domain, generated by Pulse, wrapped (encrypted) under the CMK, and stored in the `DekStore`. The domains are defined by the `DekDomain` enum:

## Implementing a Provider

### Example: AWS KMS-Backed CmkProvider

Here's how you'd build a production CMK provider using AWS KMS. Each tenant has their own KMS key, identified by a key ARN stored in a mapping.

**Add dependencies** to `pulse-server/Cargo.toml`:

```toml
aws-sdk-kms = "1"
aws-config = "1"
```

**Create `pulse-server/src/kms_cmk.rs`:**

```rust
use std::collections::HashMap;
use std::sync::Mutex;

use aws_sdk_kms::Client as KmsClient;
use aws_sdk_kms::primitives::Blob;
use pulse_protocol::TenantId;

use crate::cmk::{CmkError, CmkProvider};

pub struct KmsCmkProvider {
    client: KmsClient,
    /// Maps tenant_id -> KMS key ARN
    key_arns: Mutex<HashMap<TenantId, String>>,
}

impl KmsCmkProvider {
    pub fn new(client: KmsClient) -> Self {
        Self {
            client,
            key_arns: Mutex::new(HashMap::new()),
        }
    }

    /// Register a tenant's KMS key ARN.
    pub fn register_tenant(&self, tenant_id: TenantId, key_arn: String) {
        self.key_arns
            .lock()
            .expect("key_arns lock poisoned")
            .insert(tenant_id, key_arn);
    }

    fn key_arn(&self, tenant_id: &TenantId) -> Result<String, CmkError> {
        self.key_arns
            .lock()
            .expect("key_arns lock poisoned")
            .get(tenant_id)
            .cloned()
            .ok_or_else(|| CmkError::WrapFailed(
                format!("no KMS key ARN for tenant {tenant_id}")
            ))
    }
}

impl CmkProvider for KmsCmkProvider {
    fn wrap_dek(
        &self,
        tenant_id: &TenantId,
        plaintext_dek: &[u8; 32],
    ) -> Result<Vec<u8>, CmkError> {
        let key_arn = self.key_arn(tenant_id)?;
        tokio::task::block_in_place(|| {
            let rt = tokio::runtime::Handle::current();
            rt.block_on(async {
                let result = self.client
                    .encrypt()
                    .key_id(&key_arn)
                    .plaintext(Blob::new(plaintext_dek.to_vec()))
                    .send()
                    .await
                    .map_err(|e| CmkError::WrapFailed(e.to_string()))?;

                Ok(result.ciphertext_blob()
                    .ok_or_else(|| CmkError::WrapFailed("no ciphertext in response".into()))?
                    .as_ref()
                    .to_vec())
            })
        })
    }

    fn unwrap_dek(
        &self,
        tenant_id: &TenantId,
        wrapped_dek: &[u8],
    ) -> Result<[u8; 32], CmkError> {
        let key_arn = self.key_arn(tenant_id)?;
        tokio::task::block_in_place(|| {
            let rt = tokio::runtime::Handle::current();
            rt.block_on(async {
                let result = self.client
                    .decrypt()
                    .key_id(&key_arn)
                    .ciphertext_blob(Blob::new(wrapped_dek.to_vec()))
                    .send()
                    .await
                    .map_err(|e| CmkError::UnwrapFailed(e.to_string()))?;

                let plaintext = result.plaintext()
                    .ok_or_else(|| CmkError::UnwrapFailed(
                        "no plaintext in response".into()
                    ))?;

                let bytes: [u8; 32] = plaintext.as_ref()
                    .try_into()
                    .map_err(|_| CmkError::UnwrapFailed(
                        "unexpected DEK length from KMS".into()
                    ))?;
                Ok(bytes)
            })
        })
    }
}
```

> **Note:** This is illustrative. The exact `aws-sdk-kms` API may differ by version. The key pattern is: look up the tenant's KMS key ARN, call encrypt/decrypt, handle errors.

### Wiring Into main.rs

Add a new match arm in the CMK provider selection:

```rust
let cmk: Arc<dyn CmkProvider> = match config.cmk_provider.as_str() {
    "dev" => {
        tracing::info!("Using dev CMK provider");
        Arc::new(DevCmkProvider::new())
    }
    "aws-kms" => {
        tracing::info!("Using AWS KMS CMK provider");
        let aws_config = aws_config::load_defaults(aws_config::BehaviorVersion::latest()).await;
        let kms_client = aws_sdk_kms::Client::new(&aws_config);
        Arc::new(KmsCmkProvider::new(kms_client))
    }
    other => anyhow::bail!("unsupported PULSE_CMK_PROVIDER: {other:?}"),
};
```

Then set the environment variable:

```sh
PULSE_CMK_PROVIDER=aws-kms cargo run
```

## Crypto-Shredding

Crypto-shredding is the mechanism for making a tenant's data irrecoverable by deleting their cryptographic keys.

### How It Works

1. **Delete the CMK** -- The tenant deletes or disables their KMS key. `CmkProvider::unwrap_dek()` starts returning `CmkError::UnwrapFailed`.

2. **DEKs become un-unwrappable** -- The wrapped DEKs are still in the `DekStore`, but they cannot be decrypted without the CMK. They are meaningless ciphertext.

3. **Response blobs stay encrypted** -- The `EncryptingResponseStore` attempts to unwrap the DEK on `list()`. When it fails, it returns the response blob as-is (still envelope-encrypted). The blob is unreadable.

4. **Graceful degradation** -- `list()` does not panic or error. It returns the responses with their blobs still encrypted, allowing the system to remain operational for other tenants.

### Shredding Via DekStore

An alternative (or complementary) shredding path is to delete the wrapped DEKs from the `DekStore`:

```rust
dek_store.delete_tenant(&tenant_id);
```

This has the same effect: the `EncryptingResponseStore` cannot find the wrapped DEK, so it cannot decrypt. Both paths -- deleting the CMK or deleting the wrapped DEKs -- render data irrecoverable.

### What Cannot Be Shredded

- **Metadata** -- Tenant IDs, response counts, timestamps, and question batch IDs are stored in plaintext. Crypto-shredding does not erase metadata.
- **Blind-signature keys** -- If the blind-sig keypair is stored unencrypted (as in the dev `InMemoryTenantKeyStore`), deleting the CMK does not destroy it. In production, blind-sig keys should be encrypted under `DEK-blindsig` at rest.

## Rules

These are architectural invariants. Do not violate them.

1. **`CmkProvider` and `DekStore` live in `pulse-server` (the composition root).** They are infrastructure concerns, not domain logic. Domain crates should not depend on them.

2. **`TenantSigningKeyStore` lives in `pulse-identity`, `TenantVerificationKeyStore` lives in `pulse-signal`.** These are domain-level traits. The signing key store is an identity-zone concern (knows which key to sign with); the verification key store is a signal-zone concern (knows which key to verify against). They are never cross-imported.

3. **The CMK is never stored by Pulse.** The tenant holds their CMK in their own KMS. Pulse only calls wrap/unwrap operations through the `CmkProvider` trait. If Pulse stored the CMK, crypto-shredding would be meaningless.

4. **DEKs are stored only in their wrapped (encrypted) form.** Plaintext DEKs exist only in memory, briefly, during wrap/unwrap operations. The `DekStore` only ever persists the wrapped ciphertext.

5. **`EncryptingResponseStore` is a decorator -- compose it around any `ResponseStore`.** It adds envelope encryption transparently. The inner store sees only encrypted blobs. You can stack it on top of `InMemoryStore`, `SqliteStore`, or any future backend.

6. **The `DevCmkProvider` uses a single key for all tenants.** It exists for development and testing only. In production, each tenant must have their own CMK in their own KMS, providing true per-tenant cryptographic isolation.
